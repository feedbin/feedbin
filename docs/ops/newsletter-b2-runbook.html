Newsletter pages to B2

Spec: docs/superpowers/specs/2026-10-05-newsletter-storage-b2-design.md. Spot checks: newsletter-b2-spot-checks.html. Run each console block in a production Rails console.

Before Deploy A

  1. This runs on the code in production today. Since 2022 the saver stored NEWSLETTER_HOST plus the S3 response path. The B2 origin serves /<key> only. If the stored path holds anything else, such as an S3 bucket name, those links break at the cutover. 
    begin
  host = ENV["NEWSLETTER_HOST"]
  puts "NEWSLETTER_HOST: #{host.inspect}"
  entries = Feed.newsletter.order(id: :desc).limit(20).flat_map { it.entries.order(id: :desc).limit(5).to_a }
  on_host = entries.select { it.url.to_s.start_with?("https://#{host}/") }
  puts "entries sampled: #{entries.size}"
  puts "url on NEWSLETTER_HOST: #{on_host.size}"
  puts "url equals newsletter_url: #{on_host.count { it.url == it.newsletter_url }}"
  on_host.reject { it.url == it.newsletter_url }.first(3).each { puts "differs: #{it.url} (expected #{it.newsletter_url})" }
end
    Expect: the last two counts are equal and no "differs" lines. If they differ, stop. The stored URLs need a fix before this migration.
  2. Make a B2 bucket in the same account as the image store.
    • Set it to public.
    • Set its lifecycle to "Keep only the last version of the file". B2 keeps every version by default, and each re-save of a page would be stored and billed again.
    • Make sure the UNIFIED_* application key is allowed on this bucket. A key restricted to the image bucket is not.
  3. In 1Password, open the item feedbin in the Development vault. In the production_env field, add NEWSLETTERS_BUCKET with the name of the bucket from the previous step. Do not change AWS_S3_BUCKET_NEWSLETTERS. The saver needs it for the dual write. The deploy uploads this field as .env.

Deploy A: write to S3 and B2

  1. Capistrano deploys main from GitHub. 
    cd ~/Sites/feedbin
git switch main
git merge --ff-only newsletter
git push origin main
  2. The deploy pauses Sidekiq, uploads .env, and restarts the web and background services. There is no migration. 
    cd ~/Sites/deploy/feedbin
bundle exec cap production deploy
    From now on the saver writes each new page to S3 first, then to B2. The CDN still reads S3.
  3. Check 1 proves that the key can write to the bucket and that the bucket serves the gzip headers publicly. Check 2 runs the saver and proves that both copies were written. If either check fails, stop. New newsletters still reach S3, so nothing is broken for readers. Sidekiq retries the B2 writes once the cause is fixed.

Backfill

  1. begin
  workers = Sidekiq::ProcessSet.new.select { it["queues"].include?("backfill") }
  puts "processes on the backfill queue: #{workers.size}"
  workers.each { puts "#{it["hostname"]}: concurrency #{it["concurrency"]}" }
end
    Expect: 2 processes, concurrency 20 each.
  2. It enqueues one job for each newsletter feed. It refuses to start while an earlier pass still has jobs out. 
    begin
  NewsletterBackfill.new.build
  puts NewsletterBackfill.progress
end
  3. Run this block until pending is 0. 
    begin
  puts NewsletterBackfill.progress
  puts "queued: #{Sidekiq::Queue.new("backfill").size}"
  puts "retrying: #{Sidekiq::RetrySet.new.count { it.klass == "NewsletterBackfill" }}"
  puts "dead: #{Sidekiq::DeadSet.new.count { it.klass == "NewsletterBackfill" }}"
end
    Expect at the end: pending 0, mismatched 0, queued 0, retrying 0, dead 0.
    • A job that fails retries by itself. It counts only when it finishes.
    • If pending stays above 0 while queued and retrying are 0, some jobs are dead. Run the next step.
    • If mismatched is above 0, stop before the cutover. Those entries have a URL on NEWSLETTER_HOST that the B2 origin will not serve. Step 1 prints examples.
  4. begin
  dead = Sidekiq::DeadSet.new.select { it.klass == "NewsletterBackfill" }
  puts "dead jobs: #{dead.size}"
  dead.map { it.item["error_message"] }.uniq.first(3).each { puts "error: #{it}" }
  dead.each(&:retry)
  puts "retried: #{dead.size}"
end
    Fix the cause the errors name first. Then go back to the previous step.
  5. It samples old pages directly on B2.

Cutover

  1. Point the origin of the NEWSLETTER_HOST CDN at the B2 bucket. Map the public path /<key> to /<bucket>/<key> on the B2 endpoint. The CDN must pass Content-Encoding through and must not decompress the body.
  2. It reads new and old pages through the public host. If it fails, point the origin at S3 again. S3 still holds every page until Deploy B.

Deploy B: write to B2 only

  1. In the production_env field of the 1Password item feedbin, remove AWS_S3_BUCKET_NEWSLETTERS. A restart alone is not enough, because the env file is uploaded with each release. 
    cd ~/Sites/deploy/feedbin
bundle exec cap production deploy
  2. Expect: "S3 dual write on: false" and a fresh B2 copy. The migration is complete at this step. From now on a rollback to S3 would miss every page saved after Deploy B.
  3. When you no longer need the rollback, delete the old S3 newsletter bucket.
